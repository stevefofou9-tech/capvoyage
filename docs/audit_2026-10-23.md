## 0. Le bug « je clique, rien ne se passe » — résolu

### Cause racine (reproduite)

1. Le commit `9074eaa` (V4) contenait **deux déclarations de `showToast`** dans `src/ui/app.js` → `SyntaxError: Identifier 'showToast' has already been declared`.
   `app.js` étant un module ES, **aucune ligne ne s'exécute** : la page s'affiche (HTML/CSS), mais aucun gestionnaire de clic n'est branché.
2. Le correctif `7b8d610` a bien supprimé le doublon, **mais l'ancienne version continuait d'être servie** :
   - **Service Worker en cache-first** (`sw.js`) avec un nom de cache inchangé (`capvoyage-cache-v5`) : le navigateur recevait l'`app.js` cassé depuis le cache.
   - **En prod, `Cache-Control: max-age=86400, stale-while-revalidate=604800`** sur les JS/CSS non versionnés : même la mise à jour en arrière-plan du SW relisait le cache HTTP périmé, ce qui figeait la version cassée jusqu'à 8 jours.
3. **La prod n'a jamais reçu le correctif** : `https://capvoyage.fly.dev/app.js` sert encore la version avec le `SyntaxError` (vérifié avec `node --check`). Le dépôt n'a **aucun remote git**, donc le workflow GitHub Actions (tests et déploiement) n'a jamais tourné.

Reproduction : j'ai injecté l'ancien `app.js` dans le cache `capvoyage-cache-v5`. Résultat : la page s'affiche, `onclick = null`, la modale ne s'ouvre pas et la console montre `Uncaught SyntaxError`, soit exactement le symptôme décrit.

### Correctifs appliqués

| Fichier | Changement |
|---|---|
| `src/ui/sw.js` | Stratégie **network-first** (le cache ne sert que hors-ligne), cache `v6` (purge automatique de `v5`), préchargement avec `cache: 'reload'`, repli sur `index.html` pour une navigation hors-ligne. |
| `src/server.js` | Fichiers statiques en `Cache-Control: no-cache` + **ETag** (réponse `304` sans corps : pas de surcoût réseau). Fini le `max-age` d'un jour sur des fichiers non versionnés. |
| `src/ui/app.js` | Enregistrement du SW avec `updateViaCache: 'none'` et rechargement automatique (une seule fois) quand une nouvelle version prend la main. Suppression d'une référence morte (`btn-move-from-modal`, voir §4). |
| `tests/ui/frontend_integrity.test.js` | Nouveau test : syntaxe de tous les modules servis au navigateur (**il échoue bien sur l'ancien `app.js`**), ids `getElementById` ↔ `index.html`, SW non cache-first. |

Vérifié dans le navigateur : en partant du cache empoisonné, après un rechargement le SW v6 remplace v5, le cache v5 est purgé et le clic ouvre la modale. `npm test` : **94/94**.

### Ce qu'il reste à faire pour la prod

```bash
fly deploy
```
Ensuite, les utilisateurs déjà touchés récupèrent la bonne version **au deuxième chargement** : le premier recharge encore l'ancien SW, qui détecte et installe le nouveau. Pour qu'à l'avenir un `git push` déploie tout seul, il faut créer le dépôt GitHub, ajouter le remote et le secret `FLY_API_TOKEN`.

## 1. Sécurité & intégrité des données (serveur)

| # | Sév. | Constat | Détail |
|---|---|---|---|
| S1 | 🔴 | **N'importe qui peut écraser n'importe quel voyage (IDOR)** | `POST /api/trip` enregistre le corps reçu via `dbService.saveTrip(updatedTrip, …)` avec `ON CONFLICT(id) DO UPDATE SET user_id = excluded.user_id, data = …`. L'`id` vient du client et **aucune vérification ne contrôle que le voyage appartient à l'appelant**. Sans session, `user_id` est aussi celui envoyé dans le corps. |
| S2 | 🔴 | **Le partage « lecture seule » est contournable** | `GET /api/trip?share=…` renvoie le voyage complet (dont `id` et `userId`). Le seul verrou côté serveur est `if (updatedTrip.isReadOnly)`, un champ que le client envoie lui-même : il suffit de le retirer pour réécrire le voyage partagé. Combiné à S1, toute personne ayant un lien de partage peut modifier le voyage. |
| S3 | 🔴 | **Le voyage démo est partagé et modifiable par tous** | Une session démo (`demo-token-…`) n'est pas reconnue par le serveur, donc chaque visiteur démo écrit dans `data/trip_cameroun.json` et en base. Tous les visiteurs voient les modifications des autres. `POST /api/reset` n'est pas authentifié. Effet de bord : ce fichier **suivi par git** est réécrit à l'exécution (il est modifié en ce moment et figurait dans le dernier commit). |
| S4 | 🟠 | Rate limiting contournable | `getClientIp` fait confiance au premier élément de `X-Forwarded-For`, que le client contrôle. Sur Fly, il faut utiliser `Fly-Client-IP`. Il n'y a pas non plus de limite **par email**, ce qui rend possible le brute-force du code à 6 chiffres en changeant d'IP fictive. |
| S5 | 🟠 | Sessions sans expiration, une seule par compte | `sessionToken` n'expire jamais. Une nouvelle connexion (autre appareil) **déconnecte l'appareil précédent**, ce qui est gênant pour une app pensée « téléphone + ordinateur ». |
| S6 | 🟠 | Codes et identifiants via `Math.random()` | `generateCode()` doit utiliser `crypto.randomInt(100000, 1000000)`. Repli `Math.random` aussi pour les `shareToken`. |
| S7 | 🟠 | Connexion impossible en prod sans `RESEND_API_KEY` | Sans clé, `EmailService` ne fait que `console.log` le code, et `devCode` est masqué en prod : personne ne peut se connecter. **À vérifier** avec `fly secrets list` (je n'ai pas pu le contrôler). |
| S8 | 🟠 | Courses critiques (lost updates) | Chaque requête relit **tous** les utilisateurs, les modifie puis les réécrit tous (SQLite **et** `users.json`). Deux requêtes concurrentes peuvent s'écraser. Coût O(n) à chaque appel. |
| S9 | 🟡 | Pas de `Content-Security-Policy`, CORS `*` par défaut | Risque faible (Bearer token, pas de cookies), mais un CSP `script-src 'self'` serait une défense en profondeur peu coûteuse. |

Correctif recommandé pour S1/S2/S3 : côté serveur, charger le voyage existant par `user.currentTripId` et **ignorer l'`id`/`userId` du corps**. Refuser `POST /api/trip` sans session valide (403). Pour la démo, n'écrire que dans le `localStorage` du navigateur. Supprimer `/api/reset` en prod ou le protéger.

## 2. Architecture

| # | Sév. | Constat |
|---|---|---|
| A1 | ✅ | Couche domaine (`src/domain/*`) **pure, sans dépendance, partagée** entre navigateur et serveur. C'est le point fort du projet : la logique métier est testable et réutilisée. |
| A2 | ✅ | Zéro dépendance npm, `node:sqlite` en WAL, image Docker non-root, healthcheck, arrêt propre (SIGTERM). |
| A3 | 🟠 | **Double source de vérité** : chaque écriture va dans SQLite **et** dans des fichiers JSON (`users.json`, `trips/*.json`, `trip_<userId>.json`), avec des replis de lecture dans les deux sens. Une incohérence finira par apparaître. Il faut choisir SQLite seul et garder la migration JSON comme script ponctuel. |
| A4 | 🟠 | **Le mode hors-ligne perd les modifications** : `saveTripData()` ne vérifie pas `res.ok` et n'a **aucune file de synchronisation**. Une modification faite hors-ligne n'est jamais renvoyée, et au chargement suivant (en ligne) `loadTripData()` **écrase le cache local par la version serveur**. Cela contredit la promesse « 100 % offline-first ». Il faudrait un `updatedAt`/version, une file d'attente et une resynchronisation au retour réseau (`online`). |
| A5 | 🟠 | Synchronisation « dernier qui écrit gagne » sur le voyage **entier** à chaque frappe : deux appareils s'écrasent mutuellement. Il faut au minimum un contrôle de version (`If-Match`/`updatedAt`) avec un conflit 409. |
| A6 | 🟡 | `server.js` = routeur `if` géant de 570 lignes, qui démarre l'écoute dès l'import. Il est donc **impossible à tester en HTTP** sans lancer un port. Séparer `createServer()` de `listen()`. |
| A7 | 🟡 | `app.js` monolithique (2 660 lignes, un objet `elements` de ~150 entrées, `innerHTML` + `onclick` réassignés). Découper par écran (planning, todos, budget, contacts, auth) en modules ES ; c'est faisable sans outil de build. |
| A8 | 🟡 | Seed démo : le code cherche `getTripById('trip-cameroun-seed')`, mais `createInitialSeedTrip()` génère un UUID, donc la recherche ne trouve jamais rien et chaque `/api/reset` crée une ligne orpheline en base. |
| A9 | 🟡 | Taux de change : `api.frankfurter.app` est bloqué par CORS depuis le navigateur (erreur observée en console), donc le bouton « sync taux » échoue toujours. Frankfurter (BCE) ne publie pas XAF/XOF : sans gravité vu la parité fixe, mais l'UI devrait le dire. Proxyfier via le serveur ou utiliser `api.frankfurter.dev`. |

## 4. UX / UI

| # | Sév. | Constat |
|---|---|---|
| U1 | ✅ | Identité visuelle propre et cohérente, landing claire avec deux CTA (« Commencer » / « Démo »), ajout rapide d'idée en un champ (fidèle au PRD « enregistrement progressif »), modèles d'activités, blocs Matin/Après-midi/Soirée lisibles, dialogues natives `<dialog>` avec labels (aucun champ sans libellé détecté). |
| U2 | 🔴 | **Mobile (375 px) : la page déborde horizontalement** (largeur de défilement 709 px pour 375 px). La zone marque/titre et les onglets du header ne se compriment pas (`.nav-tabs` sans `min-width: 0`, titre sans retour à la ligne). **L'en-tête occupe 362 px, soit 45 % de l'écran**, et il est `sticky`. Les onglets du header sont en doublon avec la barre de navigation basse. C'est contraire à NFR-1 (« mobile-first »). Correctif : sous 768 px, masquer `.nav-tabs`, laisser le titre passer à la ligne, compacter les boutons d'action dans un menu, ne pas rendre le header sticky. |
| U3 | 🟠 | **Pas de retour en cas d'échec de sauvegarde** : erreur serveur ou hors-ligne, l'utilisateur croit avoir enregistré (voir A4). Un indicateur « Enregistré / En attente de synchro » est nécessaire. |
| U4 | 🟠 | **Fonction morte « Déplacer l'activité »** : `dialog-move-activity` existe mais aucun bouton ne l'ouvre (`btn-move-from-modal` n'existait pas dans le HTML). Le besoin est couvert par le sélecteur de jour de la modale d'édition, il faut donc **supprimer la modale et `openMoveModal`**. Le réordonnancement d'activités (REQ-2.3) n'est pas implémenté. |
| U5 | 🟡 | 7 cibles tactiles de moins de 32 px de haut en mobile (recommandé ≥ 44 px). Filtres de catégories sur 3 lignes en mobile : un défilement horizontal serait plus compact. |
| U6 | 🟡 | Mode démo : « Configurer Voyage » mène à l'assistant de création, ce qui est ambigu en démo. Il manque une sortie claire du mode démo vers « Créer mon compte ». |
